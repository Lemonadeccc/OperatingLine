## Catalog-grounded goal coverage

- Blender ActionCatalog `1.12.0` contains twenty-two allowlisted actions and fourteen adapter-owned `semanticCapabilities`; direct Cube, Icosphere, Torus, Cone, Cylinder, whole-mesh Subdivide/Triangulate, explicit connected face-region Extrude, Bevel/Solidify Modifier, Transform Geometry Nodes and bounded skin-weight actions make meaningful parts independently teachable while bounded batch assembly remains available. Capability-aware Planning and Replanning Packets use format `1.1.0`; historical catalogs remain replayable with packet `1.0.0`. The corresponding planning-quality baselines are `1.1.0` and `1.0.0`.
- A provider draft must declare a trace from each concrete requirement to one or more exact catalog capabilities and then to executable leaf step IDs whose actions implement those capabilities. Local replanning limits those step IDs to the normalized referenced subtrees.
- Missing coverage, unknown capabilities, nonexistent or actionless steps, action/capability mismatches, and out-of-scope replan mappings produce deterministic errors. Provider generation returns `needs_revision` with `proposalCreated: false`; the trace and report enter quality events and raw Eval/replay evidence.
- This trace is provider-authored audit evidence, not OperatingLine-owned semantic truth. It has no scalar score, does not prove requirement extraction or parameter semantics, does not select or invoke a provider, does not mutate a scene, and does not bypass Proposal review, in-host acceptance, or explicit `Start`/`Next` execution. See [ADR 0017](docs/adr/0017-catalog-grounded-goal-coverage.md).

## Interaction guidance catalog

- InteractionCatalog is a separate, host-neutral envelope over adapter-owned UI identities. Version `1.13.0` binds exactly to Blender ActionCatalog `1.12.0`, contains one recipe for each of its twenty-two actions, and preserves `1.9.0`/`1.10.0`/`1.11.0`/`1.12.0` for exact replay.
- The accepted leaf's `actionName` selects the recipe. Model-authored anchors may explain intent but cannot select or redirect a clickable host target.
- `native_path` means the exact host route and final accepted-action binding have passed supported-version tests. `semantic_path` means ordered teaching reference only; render it gray with `UI target unavailable`, leave the real host UI untouched, and keep `Next` as the execution entry point.
- The current Blender catalog has seven native recipes (Plane, Cube, UV Sphere, Icosphere, Cone, Cylinder, and Torus) and fifteen semantic recipes. Its closed UV Sphere Procedure declaration materializes the native menu path, ordered Location/Scale/Object Name controls, and a six-step candidate shortcut projection with explicit chord/sequence semantics. Icosphere independently materializes its four guidance steps followed by ordered Location and Object Name controls while preserving exact `subdivisions`, `radius`, `location`, and `objectName` values. Internal `resourceId` is omitted from UI inputs; Icosphere shortcut and every MCP track remain unavailable because no corresponding verified shortcut declaration or real action-level MCP tool exists. These are candidate teaching projections, not verified host-state equivalence. Expanding verified coverage requires observation, rollback, version gates, and Blender 4.5/5.1 execution evidence. See [ADR 0024](docs/adr/0024-versioned-interaction-catalog.md), [ADR 0046](docs/adr/0046-catalog-bound-procedure-materialization.md), [ADR 0047](docs/adr/0047-ordered-procedure-parameter-operations.md), [ADR 0048](docs/adr/0048-candidate-shortcut-procedure-materialization.md), and [ADR 0049](docs/adr/0049-icosphere-ordered-menu-materialization.md).

## Brand

- Personality: calm, precise, teachable, and visibly accountable. The UI should feel like an industrial operation guide rather than a decorative assistant.
- Trust signals: every visible state maps to an actual plan step; proposed plans are visibly distinct from accepted plans; no proposal can execute before an explicit in-host acceptance; object/world anchors point to resolved Blender data; unresolved native UI targets are described as semantic paths instead of receiving invented coordinates.
- Avoid: black primary guidance lines, color-only meaning, fake claims that deterministic data-API actions clicked Blender menus, floating desktop overlays, and visual noise that obscures the model.

## Product goals

- Goals: show completed/Back/Next/locked state; keep the hierarchy readable; provide the same accepted action through `Next` and verified native menu paths; give model clients versioned packets and strict evaluate-before-propose contracts; keep AI-authored Plans review-only until explicit acceptance; preserve structured references, parameter edits, revision DAG lineage, diffs, history and decisions in one native workspace; disclose Provider data handling and possible charges before every invocation; stream bounded assistant replies through durable short polling; and allow semantic replanning only inside the exact one-turn authorization without bypassing Proposal review.
- Non-goals: a vendor-backed default runtime, automatic Provider/model selection, long-lived consent, an arbitrary-goal task-decomposition engine, core-owned credentials, process-level isolation for in-process plugins, preservation of private model reasoning, in-place mutation of an accepted/proposed Plan, arbitrary Edit Mode/Modifier/Geometry Nodes/weight-paint/animation editing, automatic Eval scoring or data sanitization, arbitrary built-in UI-element detection, arbitrary MCP execution, and cross-host parity in this milestone.
- Success signals: MCP Prompt, MCP Tool, and HTTP reuse the same deterministic Planner Packet builder for the same context; Prompt presents the packet's rendered model text while Tool/HTTP return the complete packet; the packet requires one strict GuideProposal draft and instructs `planning.evaluate -> guide.propose`; prompt generation emits a replayable `planning.prompt.generated` event without invoking a model; an explicitly injected provider receives that exact packet and an `AbortSignal`, public listing exposes no credentials, provider selection remains explicit, and standalone remains provider-free; the optional OpenAI provider requires an explicit model and credential, uses the official Responses SDK with `store: false`, a 32,768-output-token cap, `maxRetries: 0`, cooperative cancellation and JSON Object mode, and is loaded only by the separate `pnpm dev:openai` composition root; output is reparsed as an untrusted strict draft, checked against immutable packet identity, nested ActionCatalog arguments and the same deterministic planning-quality gate, then returned with `proposalCreated: false`; failed or interrupted request IDs require a new explicit ID for retry; generation requested/completed/failed evidence is replayable without persisting raw provider errors or private reasoning; the same deterministic gate rejects invalid phase trees or resource flow before Proposal submission; evaluation emits `planning.quality.evaluated` without a scalar score; snowman and robot references pass while the robot intentionally omits animation; a referenced revision request contains the exact base Plan, stable node IDs plus display numbers, user message, thread ID, turn and parent; exact retries are idempotent; a continued turn must use an accepted parent Proposal in the same instance as its exact base and cannot branch silently; an MCP client can list pending requests or build the exact Replanning Prompt Packet, explicitly invoke a provider's typed `replan()`, receive a complete candidate plus deterministic diff/locality/quality with `proposalCreated: false`, and submit only that canonical generated draft as a request-linked Proposal in a separate call; another generation cannot claim its provenance; Blender's Revision Workspace keeps structured references separate from the message, supports per-reference removal, retains but blocks a draft after a base mismatch, keeps thread/provider-run/proposal/diff/decision together, and remains available when Guidance is hidden; after runtime acknowledgement it lists Provider descriptors without credentials, leaves selection empty, explains transmission and possible charges, and requires a fresh host confirmation for every Run or retry; Run start returns promptly while Orchestrator performs generate and exact canonical propose asynchronously; one instance cannot hide concurrent runs or Proposals; interrupted runs never silently invoke the Provider again; request submission, history retrieval, Replan Run states, proposal preview, and provider generation do not mutate the scene or active session; the replacement proposal still requires explicit in-host acceptance; replay export preserves target, prompt contract, generated draft, exact catalog, quality/locality findings, proposal, diff, decision, observation and rollback with a stable cursor and deterministic content hash; Blender 4.5 LTS and 5.1 tests pass.

## Personas and jobs

- Primary personas: Blender beginners supervising AI-assisted work; experienced Blender users auditing or correcting a generated sequence; adapter developers implementing another host companion.
- User jobs: understand the overall task tree; review the hierarchy and executable leaves proposed by an AI; reference one or more nodes without copying fragile text; explain the desired change in host context; know which Plan revision and revision turn are being discussed; review earlier requests, returned revisions, diffs, and decisions; inspect exactly which Plan fields, nodes and simple parameters changed; accept or reject the resulting proposal inside the host; predict the next mutation before executing it; identify the exact step Back will compensate; temporarily remove guidance without losing task state.
- Key contexts of use: Blender's 3D View with a narrow Sidebar, light or dark Blender themes, rendered or solid shading, and scenes containing user-owned objects that must not be mistaken for OperatingLine resources.

## Information architecture

- Primary navigation: Blender's `N` Sidebar contains one `OperatingLine` tab. It is the stable control surface; the viewport overlay is contextual guidance, not navigation.
- Core routes/screens: connection status; collapsible Revision Workspace containing draft context, structured references, message, Provider disclosure and Run status, thread history, pending proposal, diff, and decision; safety option; walkthrough controls; guidance visibility; current Back/Next status; proposal tree; and accepted task tree.
- Content hierarchy: connection first; Revision Workspace second, with current draft and acknowledged request before Provider choice/disclosure/Run state, followed by the related thread/proposal/diff/decision log; safety and accepted-plan Start/Back/Next controls third; guidance visibility fourth; current status fifth; proposed and accepted trees after the workspace that receives their references; detailed protocol/diagnostic text last. Collapsing the workspace hides its detail without deleting draft, Run, proposal, or review state.

## Design principles

- State before decoration: every color, number, icon, and line represents a deterministic state derived from `active_index`.
- Review before mutation: receiving and validating a proposal only creates an in-memory preview. Accept is the sole transition that may replace an idle active session; Reject only records the decision and clears the preview.
- Reference before revision: node numbers are readable locators, but immutable requests bind the complete base Plan, stable node IDs and a linear thread turn. A model response is a new complete proposal plus a derived review diff, never an in-place tree mutation or executable patch.
- Preserve before rebasing: selecting a node from a different active/proposed Plan base must not silently delete or rebind the user's references or message. Reject that selection and require a deliberate Clear Draft before switching bases.
- Disclose before transmission: a Provider descriptor informs but does not authorize. Leave Provider selection empty, show execution location, data handling, payload scope and possible-charge language, then require a fresh native confirmation for each invocation or retry.
- Honest anchors: resolve model/world targets when possible. A versioned InteractionCatalog, selected by the accepted leaf action rather than an AI-authored anchor, owns each ordered host path. An allowlisted, version-tested `native_path` may annotate real menu labels and route its final item into the exact accepted action; every `semantic_path` and unmatched `operator.menuPath` remains an explicitly unavailable breadcrumb. Never infer arbitrary widget rectangles or draw a plausible but false line.
- Progressive focus: show at most the most relevant completed, Back, and Next steps in the viewport while retaining the complete hierarchy in the Sidebar.
- Host-native control: use Blender Panel, Operator, draw handler, `gpu`, and `blf`; do not depend on a transparent Electron window over Blender.
- Tradeoffs: Blender `UILayout` does not expose arbitrary per-button text/background colors or stable rectangles for every built-in widget. The guided header entry therefore uses Blender's native blue depressed background for CURRENT and red `alert` background for the immediate previous/BACK state. NEXT uses the built-in green color block and explicit text because Blender exposes no per-button green background. The enlarged viewport card owns the exact red/green/blue/gray filled badges, lines, and labels. The `Layout` workspace context is shown truthfully in that card rather than positioned with guessed tab coordinates; reserve arbitrary cross-region arrows or custom gizmos for a later interactive-anchor milestone.

## Visual language

- Color: `surface #101820`, `halo #071018`, `text #F5F7FA`, `completed #2F9BFF`, `current #FFC857`, `next #2DD881`, `back #FF5C6C`, and `locked #7B8494`. Black/dark halo may outline a colored line but is never the primary line.
- Typography: inherit Blender UI fonts in the Sidebar; use Blender's `blf` default font in the viewport. The viewport status title is at least 18 px and its Back/Next copy at least 15 px at Blender UI scale 1.0. Global executable ordinals use two digits (`01`–`25`); menu microsteps use `01`–`04`; tree nodes retain hierarchy numbers (`1.2.1`).
- Spacing/layout rhythm: use Blender-native row/box spacing. The viewport card keeps at least 16 px from an edge, is large enough for readable status plus one four-item menu path, uses at least a 40 px circular global-step marker, and prioritizes one Back and one Next item.
- Shape/radius/elevation: native Sidebar surfaces; flat, high-contrast viewport cards; circular ordinal badges with a dark outer ring and colored inner fill.
- Motion: the scene may contain explicit plan-authored keyframes, but the guidance UI has no required motion. Any later UI transition must respect reduced-motion settings and must not delay execution feedback.
- Imagery/iconography: `✓`/check for completed, `↶`/Back for the reversible active step, `▶`/Next for the next executable step, and an open circle for locked. Text labels duplicate all icon meaning.

Opening `Add` or hovering/opening `Mesh` changes only these transient roles and never the accepted action index or scene. Proposal lifecycle uses `available`, `accepted`, and `rejected`; request-linked proposals additionally use `diff_available`. Provider handoff uses `provider_unselected`, `provider_selected`, `authorization_required`, `queued`, `generating`, `proposal_created`, `needs_revision`, `failed`, and `interrupted`; retries always return to `authorization_required` with a new generation ID. Revision-history turns use `awaiting_proposal`, `awaiting_decision`, `accepted`, and `rejected`, plus loading/complete pagination copy. Synchronous Blender actions do not pretend to display a state that cannot be rendered during execution.

## Accessibility

- Target standard: WCAG 2.2 AA contrast intent where Blender's host rendering allows it; no meaning depends on red/green alone.
- Keyboard/focus behavior: retain native Blender operators so keyboard search and focus behavior remain host-managed. The overlay itself is informational and non-interactive; the guided final menu item is a native Blender Operator with the same accepted-plan and rollback gates as `Next`.
- Contrast/readability: colored lines receive a 10 px dark halo below a 4 px state-colored stroke; markers combine color, ordinal, and symbol; text uses high-contrast light foreground on the dark card.
- Screen-reader semantics: Blender's Python UI API has limited assistive-semantic controls. Operator labels and descriptions must remain explicit (`Back: ...`, `Next: ...`) and avoid icon-only controls.
- Reduced motion and sensory considerations: no flashing or required guidance animation; status changes are immediate and persistent. Scene animation is a user-visible output and can be inspected as discrete keyframes.

## Responsive behavior

- Supported breakpoints/devices: Blender desktop UI at supported 4.5 LTS and 5.1 versions; mouse/keyboard workflows; no mobile or touch target in this milestone.
- Layout adaptations: compact control labels follow Blender-native sizing in a narrow Sidebar; Revision Workspace can collapse to a one-row summary without losing state; structured references wrap independently from the message and each keeps a reachable Remove control; exact revision messages wrap inside their log entries instead of being truncated; viewport anchors clamp to its visible region; the card avoids the Sidebar edge and limits contextual items instead of rendering all 25 lines.
- Touch/hover differences: opening the allowlisted `Add` menu and opening its `Mesh` submenu progressively reveal the next microstep. No hover-only fact is required to execute: the card retains the complete path and native operator descriptions provide tooltips.

## Interaction states

- Loading: Companion connection uses existing status text; deterministic local actions are synchronous and do not show a fake loading animation.
- Empty: before Start or after a full rollback, step `01` is green Next and Back is disabled.
- Goal entry: when no goal/revision/Proposal review owns the slot, show one collapsible `Goal to Guidance` section with a natural-language field and `Create Guidance`. Submission requires a connected Runtime, trims the goal, clears the field only after the immutable request enters the local transport queue, and never selects a Provider.
- Goal request local/delivering: show the stable short request ID and state explicitly that the scene and active Plan are unchanged. Network retry reuses the same request payload and ID; do not create a second visual request or imply that a model is running.
- Goal request awaiting planner: Runtime acknowledgement means only “stored for an MCP planner.” Do not show generation progress, a Provider identity, price, semantic confidence, or an ETA that the Runtime cannot prove.
- Goal request proposal received: keep the request status visible and direct the user to the existing full read-only Proposal tree and Accept/Reject gate. Only a Proposal with the exact active `goalRequestId`, instance, catalog and reserved Plan ID may advance this state.
- Proposal available: show its title, plan ID/revision, target adapter, optional revision thread, deterministic `+ / - / ~ / moved` summary, changed nodes/fields/simple parameters, read-only hierarchy, and explicit Accept/Reject controls. Do not draw viewport target lines for unaccepted steps because their object anchors may not exist yet.
- Proposal blocked: when the accepted session owns receipts, keep the proposal visible, disable Accept, disable Start/Next, preserve Back, and explain that the user must return the current walkthrough to its start before accepting.
- Proposal accepted: atomically replace only an idle accepted session, clear the preview, record the decision, and emit the existing `plan_loaded` state report before any action can run.
- Proposal rejected: clear the preview, record the decision, preserve the active session, receipts, scene, overlay state, and current step.
- Revision Workspace collapsed: keep a compact industrial-log summary with draft/reference count or latest thread state. Hide only workspace detail; do not discard draft, proposal, history, diff, or decision state, and do not couple this toggle to Guidance visibility.
- Revision request empty: show the current base Plan and `Select Ref on a task node`; Send is disabled.
- Revision request draft: show up to eight structured `@number title` reference rows above, not inside, the user-editable message field. Each row has an individual Remove action. Show the new/continued thread and next turn. `Ref` targets the proposed tree when one is pending, otherwise the active tree.
- Revision request base mismatch: if the user selects a node from the other visible active/proposed base, retain the message and existing references, report that the draft is already bound, and require Clear Draft before switching. Lifecycle actions that deliberately accept, reject, replace, or disconnect a Plan retain their existing safety cleanup/rebind rules.
- Revision request queued: clear the draft only after it enters the authenticated transport queue; show the request ID and state that no scene change occurred.
- Revision request acknowledged: state that an MCP planner may now read it; do not imply a response time or completion.
- Provider unselected/unavailable: after request acknowledgement, list only runtime descriptors and select none by default. Keep the external MCP path valid. Unavailable Providers remain visible with their reason but cannot start a Run.
- Provider selected: show exact display name/version/description and distinguish `local + no transmission` from `remote + provider-managed transmission`. For remote execution, state that the revision message, complete base Plan and references, ActionCatalog, and latest Companion state are sent; state that Provider use may incur charges and OperatingLine cannot estimate them.
- Provider authorization: `Confirm Provider Run` opens a native confirmation for this invocation only; a retry is labeled `Confirm New Provider Run`. Confirmation authorizes the selected Provider call and, only if its canonical result is ready, creation of one review Proposal. Changing Provider/request, disconnecting, reaching a terminal state, or retrying invalidates the confirmation; no persistent consent toggle exists.
- Replan Run queued/generating: poll a short-lived status resource while keeping Companion guide, report, history, accepted-plan, and walkthrough controls responsive. To preserve the identity of a potentially billable invocation, disable a second revision submission, Provider refresh, and any concurrently delivered Proposal decision until the Run becomes terminal; draft edits remain local. Ordinary Plan or Proposal delivery and an exact duplicate acknowledgement must not clear or impersonate the active Run. These states never imply a scene or active-session change and do not expose private model reasoning. `proposal_created` hands review back to the existing Proposal delivery and Accept/Reject lifecycle.
- Replan Run needs revision/failed: show deterministic findings or a sanitized stable error plus retry guidance. Retry keeps the acknowledged revision request, creates a new generation UUID, and requires a new confirmation; it never silently repeats a possibly paid call.
- Replan proposal available: display source request ID, thread/turn, exact diff, and Accept/Reject decision in the same Revision Workspace as the originating request; it remains non-executable until Accept. Accepting it records lineage for the next active-plan request.
- Dialogue Provider unselected/selected: use a separate provider list, leave it unselected after discovery, and show the selected descriptor plus transmission, possible-charge, fixed `0.8`, two-call maximum and Proposal-only disclosures before enabling confirmation.
- Dialogue queued/streaming: show the exact authorized Provider and append-only assistant text from durable short polling. A partial failed or interrupted stream remains visible for diagnosis but never enters the next turn's complete history.
- Dialogue answered: preserve the complete user/assistant pair in the bounded recent history and state that no revision request or Proposal was created.
- Dialogue replanning: state that the threshold was met, the candidate request is now durable and the second/final authorized call is preparing a review-only Proposal. Do not offer a second Dialogue turn while this state is active.
- Dialogue needs revision/failed after request storage: keep the Dialogue turn closed and transfer the same durable revision request to the ordinary Replan Run, where another Provider generation requires a new explicit confirmation and generation UUID.
- Dialogue Proposal available/rejected: bind only the exact `(revisionRequestId, proposalId)`, including promotion of a same-request Proposal that arrived before a failed terminal status. Accept installs only the Plan; Reject preserves the active Plan and requires the next Dialogue authorization to open a fresh revision thread, or an explicit Fork from an accepted lineage.
- Revision history available: in the same Revision Workspace, show the exact user message and structured references, returned plan revision/diff summary, and derived decision state for each loaded turn. Collapse to the latest three by default, expand all loaded turns on request, and expose Load Older Turns only when the protocol page has a continuation cursor. History is an industrial operation log, is read-only, and never implies live chat or captured model reasoning.
- Error: retain the existing explicit Operator/Companion error report; do not advance visual state when an action or rollback fails.
- Success: steps before `active_index` are blue completed; `active_index` is red Back; `active_index + 1` is green Next.
- Guided menu available: keep `Next` enabled, show the real allowlisted `Add`/`Mesh`/primitive labels with microstep ordinals, and show the same four-step path on the enlarged viewport card. The menu path is an additional entry point, not a separate execution mode.
- Guided menu unsupported: do not patch or replace an unrelated built-in item. Keep `Next` unchanged and show the action's InteractionCatalog `semantic_path` as gray ordered badges with `UI target unavailable`; only fall back to the Plan `menuPath` text when no recipe exists.
- Disabled: future steps are gray locked; Back is disabled before any step; Next is disabled after the last step.
- Offline/slow network, if applicable: offline mode continues with the last accepted or bundled plan; network state must not block accepted-plan guidance controls when no proposal decision is pending. Normal UI Disconnect preserves a staged proposal, its goal correlation, pending exact decision payloads, and active revision draft for reconnect; Extension unregister explicitly clears process-local state.

## Content voice

- Tone: short, instructional, factual, and explicit about consequences.
- Terminology: `Goal to Guidance`, `Create Guidance`, `Revision Workspace`, `Plan proposal`, `Revision request`, `Provider`, `Confirm Provider Run`, `Confirm New Provider Run`, `Streamed model dialogue`, `Dialogue Turn`, `Initial Plan Run`, `Replan Run`, `Reference`, `Remove reference`, `Send request`, `Accept Plan`, `Reject Plan`, `Active plan`, `Guidance`, `Back`, `Next`, `Completed`, `Locked`, `UI target unavailable`, `Menu path`, and protocol step numbers. Call persisted revision history an operation log rather than private model reasoning; avoid `Publish` for an unapproved AI proposal and distinguish Blender native Undo/Redo from OperatingLine's receipt compensation.
- Microcopy rules: Proposal, request and Run text says that no scene change has occurred; queued request means stored for a planner, while queued Run means authorized background work; descriptor text never claims consent, exact pricing, retention policy or sandboxing; collapse/expand copy never implies deletion; a base mismatch names both revisions and the explicit action required; Accept names the plan that will become active; Next describes the mutation that will occur; Back names the mutation that will be compensated; structured reference rows display `@number title` while payloads retain stable node IDs, and the free-form message never duplicates hidden reference syntax; English UI strings remain concise until repository-wide localization is introduced.

## Implementation constraints

- Framework/styling system: Blender Python Extension APIs only for the in-host surface. Electron is not part of the Blender visual layer.
- Design-token constraints: Sidebar colors must use APIs supported by both Blender versions; viewport colors use centralized RGBA tokens. Native menu annotations use label text, Blender's red `alert` and blue `depress` states, and built-in color-block icons because `UILayout` has no public arbitrary per-control text/background color API. Do not ship per-theme pixel coordinates or mutate the user's global theme.
- Performance constraints: draw callbacks perform no network calls or scene mutation, derive only a small relevant-step window, and avoid persistent per-frame allocations where practical.
- Compatibility constraints: use public Blender 4.5/5.1 APIs; keep host-neutral protocol anchors semantic; bind native UI only through an exact versioned InteractionCatalog recipe selected from the accepted action; limit native menu replacement to recipes whose built-in menu structure is verified on both supported versions; restore every patched class label/draw method on Guidance hide and Extension unregister; do not require a Blender Core PR.
- Proposal/request constraints: proposal delivery shares the authenticated loopback poll; proposal, decision, goal/request/thread/diff/history and Initial/Replan/Dialogue Run payloads are strict, versioned, persisted and instance-bound. A Run POST persists one exact authorization and returns promptly. Dialogue authorization binds distinct dialogue/revision/generation UUIDs, a selected Provider version, complete immutable candidate request, up to twelve alternating 4000-character messages, a two-call maximum and fixed semantic threshold. The first call streams append-only assistant text; only a nonblank strict replan decision at or above `0.8` atomically stores the candidate request and may invoke one typed replan. Candidate request IDs remain reserved even after answer/failure, and immutable request/provider/authorization evidence cannot change during transitions. A stored request that fails later is recovered only through a newly authorized generation on that same request; a rejected Proposal is followed by a fresh thread or explicit Fork. Every targeted Proposal writer atomically competes for one unresolved slot; Blender binds exact result identities and promotes a cached same-request Proposal after a losing Dialogue race. Accept/Reject creates one stable decision payload on the main thread. Restart reconciliation never repeats an uncertain Provider call. The background thread handles only short HTTP operations; all host validation, preview, decision and session transitions occur on Blender's main thread.
- Provider constraints: providers are optional in-process dependencies supplied only through `startRuntime`; standalone remains provider-free. Public descriptors contain no secrets and disclose execution location, transmission and provider-owned credential management. `generate()`, optional `replan()` and optional `dialogue()` all receive strict packets plus a cooperative `AbortSignal`; core reparses unknown results, enforces bounded sizes, immutable identities, catalog arguments, deterministic quality and replan locality. The OpenAI plugin requires an explicit key/model and `maxRetries: 0`. Initial/replan generation uses non-streaming JSON Object mode; dialogue uses `store: false`, streaming text plus one strict `request_replan` tool with parallel tool calls disabled. Provider output never replaces core validation. `services/openai-runtime` remains a separate opt-in composition root. In-process injection is not a security sandbox; successful text/drafts may be sensitive. Failed, timed-out or interrupted invocation IDs are never silently repeated.
- Eval constraints: export is an authenticated, paginated Orchestrator surface rather than Blender UI state. It scopes instance-specific decisions and reports, includes generated initial/replanning packets, provider-generated strict drafts, exact referenced catalogs, raw deterministic planning-quality/locality findings, explicit initial/replan generation-to-proposal provenance, and instance-scoped Initial Plan Run evidence; it marks raw content as unredacted and never upgrades prompt generation, generation status, structure/locality findings, or observation telemetry into a semantic quality score. Random export envelope metadata is excluded from the deterministic content digest.
- Test/screenshot expectations: full lint/typecheck/Vitest/Schema/format gates; targeted provider/protocol/persistence/orchestrator tests for strict streamed output, 4000-character boundaries, fixed threshold, two-call limit, candidate reservation, immutable authorization, restart and Proposal races; Blender pure tests plus real 4.5/5.1 integration for dialogue recovery, Proposal review, native Undo, bounded Edit/Modifier/Geometry Nodes, skin weights, animation, observation gates, rendering and rollback; and visual captures for provider-free, disclosure, streaming, failure and Proposal-review states.

## Open questions

- [ ] Should a later interactive milestone use a `GizmoGroup` for clickable OperatingLine-owned viewport controls? / Product / Changes interaction architecture, not this vertical slice.
- [ ] Which second open-source host will validate the protocol's cross-host semantics? / Product and adapter research / Required before claiming general host support.
- [ ] Which human-labeled goals and acceptance rubric should validate semantic completeness beyond the deterministic structure gate? / Product and evaluation research / Required before claiming arbitrary-goal planning quality.
- [x] Which explicit provider/plugin contract should optionally execute Planner Packets without putting credentials or data-transfer policy in the core Orchestrator? / Resolved by explicit in-process injection, provider-owned credentials and transmission, strict untrusted-output validation, no auto-propose, and provider-free standalone; see ADR 0013. A future out-of-process plugin may strengthen isolation without changing the public generation contract.
- [x] How should the first vendor adapter call OpenAI without changing the provider-neutral default? / Resolved by an optional official-SDK Responses provider, explicit model/key, JSON Object mode followed by core strict validation, disabled SDK retries, cooperative cancellation, and a separate opt-in composition root; see ADR 0014.
- [x] Which versioned action-catalog schema should planners query before generating plans for a host? / Resolved by adapter-owned ActionCatalog plus `operatingline.planning.context`; see ADR 0005.
- [x] How should a node reference such as `1.1.5` become an immutable patch request and a new proposal revision? / Stable node ID + display number, complete immutable base Plan, persisted RevisionRequest, and a linked newer full GuideProposal; no in-place patch.
- [x] How should Blender explicitly authorize a long Provider replan without freezing Companion polling or bypassing Proposal review? / Resolved by a host-mediated asynchronous Replan Run with per-call disclosure confirmation, persisted lifecycle, short status polling, canonical generate-to-propose composition, new-ID retry, and unchanged Accept/Reject execution boundary; see ADR 0016.
- [ ] Should localization begin with Chinese/English UI strings or wait for the second host? / Product / Affects string ownership and screenshot baselines.
- [x] Which parameter fields can safely become host-native editable controls while still producing a complete new Proposal revision? / Resolved by catalog-derived boolean/integer/number/enum/fixed-vector controls and exact before/after edits; strings and nested records stay read-only. See ADR 0033.
- [x] Can a Blender-version-specific adapter safely guide selected built-in menu items without fixed pixels? / Resolved for allowlisted `Add > Mesh > primitive` paths by native menu labels, right-side ordinal/state controls, and a guided final Operator on Blender 4.5/5.1. Arbitrary widget rectangles, exact workspace-tab badges, arbitrary cross-region lines, and non-allowlisted menus remain unsupported and use the semantic fallback.
